# Початок зрізу

Канонічний текст команди. Claude Code викликає його через `/slice-start`,
Codex — через скіл `slice-start` (`.agents/skills/slice-start/`).

Правила циклу — `RulesForAIVibeCoding.md`, розділ *Work cycle*. Тут не переказ
правил, а порядок дій на старті сесії.

## Виконай по кроках

1. Прочитай `RulesForAIVibeCoding.md`. Якщо його немає — зупинись і скажи мені.
2. Візьми наступну роботу зі статусом `TODO` (або ту, яку я назвав), у такому
   порядку:

   * спершу `TASK-*` зі статусом `TODO`, від яких залежить наступний зріз —
     тулчейн і борг ідуть попереду функціональності;
   * потім зріз, **усі залежності якого `DONE`**;
   * `TASK-*`, від яких не залежить жоден зріз (бекап за `NFR-*`, борг,
     інструменти `deploy/`), — теж робота, а не залишок: бери, коли її
     залежності `DONE`, у порядку Release Plan. Якщо з нього не видно, чи її
     черга раніше за наступний зріз, — спитай мене.

   Зріз із незавершеною залежністю не бери: назви його, назви причину й візьми
   наступний придатний. Зріз чи задача зі статусом `BLOCKED` — так само, доки не
   сталося одне з двох: я сказав, що блок знято, або всі записи в
   `docs/OPEN-QUESTIONS.md`, чиє поле `**Блокує:**` його називає, стали
   `ANSWERED`. Якщо такого запису немає жодного, зріз не розблокований, а
   втратив причину: не бери його, скажи мені. Розблокований зріз береш у роботу одразу — на кроці 11 він
   стає `IN PROGRESS` (правила, розділ *Work cycle*, підрозділ «If the slice
   could not be finished»). Якщо придатних немає — скажи це й зупинись.

   Задачу релізу (`**Тип:** release`) цією командою не бери, навіть якщо я її
   назвав: реліз іде лише за моєю командою деплою і має два коміти — правила,
   розділ *Environments*, підрозділ *Releases and deployment*. Скажи це й
   зупинись.

   Перевір `git branch --show-current` і `git branch --list 'wip/*'`. Сесія
   стоїть не на `main` — скажи це й перейди на нього (`git switch main`) до
   будь-яких правок. Гілка з ID вимоги взятого зрізу (у задачі — з ID задачі,
   навіть якщо вона реалізує вимогу) — це його незавершена робота з
   попередньої сесії: скажи про неї.
   Продовжують її з `main` через `git merge --squash <гілка>` (правила, розділ
   *Work cycle*, підрозділ *Branching*), а не з нуля. Решту `wip/`-гілок
   просто назви.
3. Випиши: ID зрізу, які вимоги він закриває — це поле `**Вимоги:**` і лише
   воно, — від чого залежить, що у нього в «Поза обсягом».
4. **Знайди в `docs/FRS.md` кожен із цих ID пошуком** і прочитай те, що
   навколо. Не читай FRS цілком «про запас» і не переказуй по пам'яті —
   вигадані `FR-0XX` і майже-правильні AC народжуються саме так.
5. Витягни Acceptance Criteria цих `FR-*` дослівно, з ID кожного.
   Якщо AC немає, він неперевірюваний, або ти не можеш знайти ID —
   **скажи це прямо**. Реконструйований тобою AC гірший за відсутній,
   бо має вигляд домовленості.
6. Прочитай у `docs/ARCHITECTURE.md` тільки ті розділи, що стосуються зрізу
   (стек, контракти, структура, команда локальної перевірки).
7. Перевір `docs/OPEN-QUESTIONS.md`: чи не називає зріз поле `**Блокує:**`
   відкритого питання. Називає, а зріз не `BLOCKED` і я не казав, що блок
   знято, — не бери його: назви питання й спитай мене. Відкрите питання, що
   називає лише вимогу зрізу, а ні зрізу, ні «не блокує», `scripts/check-ids.py`
   у коміт не пропускає; якщо бачиш таке — теж скажи мені: чи блокує воно
   зріз, вирішую я, а не ти.
8. Назви все, що тобі неясно. Невідоме — це питання до мене,
   а не припущення (правила, розділ *The Golden Rule*). Кожен ID у питанні —
   з коротким описом у дужках, і саме питання по суті, щоб я міг відповісти
   не відкриваючи FRS (правила, розділ *Asking questions*).
9. Якщо рішення нетривіальне — покажи варіанти у форматі з розділу
   *Work cycle*. Якщо адекватний варіант справді один — скажи це одним
   рядком і поясни чому. Не добирай третій «для симетрії»:
   у вигаданого варіанта вартість теж вигадана.
10. **Зупинись і чекай на мій вибір. Не пиши код на цьому кроці.**
11. Після мого вибору, перед першим рядком коду, постав у `docs/BACKLOG.md`
    зрізу `**Статус:** IN PROGRESS` (і в Coverage Map, якщо статус там
    продубльовано; розблокований зріз — ще й прибери з таблиці *Blocked*).
    Закомітиться він разом із кодом, уже як
    `DONE`; якщо зріз не завершиться — правила, розділ *Work cycle*, підрозділ
    «If the slice could not be finished».

## Формат відповіді

Для задачі (`TASK-*`) кроки 4–5 залежать від поля `**Вимоги:**`. Задача без
нього (тулчейн, CI, борг) не має ні вимоги, ні AC — кроки 4–5 пропусти. Задача
з ним (`**Вимоги:** NFR-004` — бекап, локалізація, cron) реалізує вимогу, тож
кроки 4–5 для цих ID виконуються так само, як для зрізу: без прочитаного
тексту вимоги її реалізація — вигадка. `check-slice.py` вимагатиме тест із цим
ID у назві: під `source/`, або під `deploy/`, якщо вимогу реалізує інструмент
релізу. Якщо тестом її не перевірити взагалі (налаштування хостингу, ручна
процедура), це питання до мене і запис у `docs/OPEN-QUESTIONS.md`, а не тест
«для галочки»: вимога, яку не можна перевірити, — діра у FRS, і задача до
відповіді закривається як `BLOCKED`, а не `DONE`. Якщо я відповів, що вимогу
перевіряю вручну, задача після розблокування закривається як `DONE` з полем
`**Перевірка вручну:** NFR-004 — OQ-0XX` (правила, розділ *Work cycle*,
підрозділ *Definition of Done*): `check-slice.py` зарахує його лише з тим
записом, на якому задачу блокували, — уже закоміченим і тепер `ANSWERED`.

```
Задача:    TASK-0XX — <назва>
Навіщо:    <SLICE-0XX (<опис у 3-4 слова>) — що саме розблоковує>
Вимоги:    — / NFR-0XX (<опис у 3-4 слова>)
AC:        — / AC-0XX: <дослівно з FRS>
Обсяг:     <з BACKLOG>
Готово коли: <перевірювана умова з BACKLOG>

Неясно:
- <питання по суті; кожен ID у ньому — з описом у дужках>
```

Для зрізу:

```
Зріз:      SLICE-0XX — <назва>
Закриває:  FR-0XX (<опис у 3-4 слова>), FR-0YY (<опис>)
Залежить:  — / SLICE-0ZZ (<опис>, DONE)
AC:        AC-0XX: <дослівно з FRS>
           AC-0YY: НЕ ЗНАЙДЕНО у FRS
Поза обсягом: <з BACKLOG>

Неясно:
- <питання по суті; кожен ID у ньому — з описом у дужках>

Варіанти (якщо потрібні):
A. ... — плюси / мінуси / вартість
B. ... — плюси / мінуси / вартість
Рекомендація: ...
```
