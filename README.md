# Project Template — AI Vibe Coding

Шаблон проєкту для соло-розробки з ШІ-агентом (Claude Code / Codex).
Три підготовчі сесії в чаті створюють документацію, далі агент у репозиторії
крутить цикл розробки за фіксованими правилами.

Правила живуть в одному місці — **`RulesForAIVibeCoding.md`**, англійською.
Цей README їх не переказує, лише пояснює, як шаблоном користуватися.

## Структура

```
RulesForAIVibeCoding.md   правила циклу розробки — PRIORITY, не змінювати
AGENTS.md                 тонкий вказівник на правила (читає Codex)
CLAUDE.md                 імпорт AGENTS.md + правил (читає Claude Code)
prompts/                  промти для підготовчих сесій у чаті
prompts/dev/              дві команди циклу — канонічний текст
docs/                     документація проєкту (DEPLOY.md — з першого релізу)
scripts/                  три перевірки + маніфест хешів
source/                   код проєкту
deploy/                   install / update / rollback — з'являється перед першим деплоєм
tmpBin/                   інструменти розробки — у .gitignore
.githooks/                commit-msg (формат коміту) + pre-commit (цілісність + ID)
.github/workflows/        ті самі перевірки на сервері — --no-verify їх не дістає
.claude/settings.json     дозволи Claude Code — комітиться
.claude/commands/         /slice-start і /slice-finish — вказівники на prompts/dev/
.claude/hooks/            те, чого не вміють патерни дозволів: bash-guard + stop-integrity
.agents/skills/           ті самі дві команди для Codex — теж вказівники
.gitattributes            LF примусово; без нього хеші ламаються на Windows
```

Про вказівники: Claude Code читає `CLAUDE.md`, Codex читає `AGENTS.md`.
Тому канонічний файл один — `AGENTS.md`, а `CLAUDE.md` складається з двох
рядків-імпортів. Копій правил у репозиторії немає, розходитися нема чому.
Так само з командами циклу: канонічний текст у `prompts/dev/`, а
`.claude/commands/` і `.agents/skills/` — вказівники на нього.

## Порядок роботи

### Крок 0.0 — перевірка інструментів

Виконати **до всього іншого**. Дві команди, обидві мають вивести номер версії:

```bash
git --version
python3 --version
```

**Windows:** запускати в **Git Bash** (правий клік у папці → *Open Git Bash
here*; у Windows 11 спершу «Показати додаткові параметри»). PowerShell і cmd
не підходять — хуки починаються з `#!/bin/sh`.

Що вважається провалом:

| Вивід `python3 --version` | Що це означає |
|---|---|
| `Python 3.11.x` і вище | усе гаразд, ідіть далі |
| `Python` без номера, порожньо, або відкрився Microsoft Store | заглушка Windows — див. розділ *Windows* |
| `command not found` | Python не встановлений або не в PATH |

Заглушку треба прибрати саме тут, а не пізніше. Вона не просто не працює — вона
ламає запобіжник: `pre-commit` уміє перемикатися з `python3` на `python`, але
вибирає за `command -v python3`, а заглушка на цю перевірку відповідає «є».
Тобто коміти проходитимуть із мертвою перевіркою цілісності, і ви цього не
побачите.

Полагодити — розділ *Windows* наприкінці цього файлу. Поверніться сюди, коли
`python3 --version` віддасть номер версії.

### Крок 0 — підготовка

Основний сценарій — **template repository на GitHub**. Розкладається на разове
налаштування і два рядки на кожен наступний проєкт. Два ручні сценарії нижче —
для випадків, коли GitHub недоступний.

#### Разово: викласти шаблон

Створіть на GitHub порожній репозиторій `project-template` — без README, без
`.gitignore`, без ліцензії.

```bash
mkdir project-template && cd project-template
# розпакувати сюди ВМІСТ папки project-template з архіву
git init
git config core.hooksPath .githooks
python3 scripts/check-template.py          # має бути OK (+ WARN про порожні докси)
git add . && git commit -m "chore: TASK-000 project template"
git branch -M main
git remote add origin https://github.com/<ви>/project-template.git
git push -u origin main
```

Після пуша загляньте у вкладку **Actions**: `template-check` має пройти зелено.
Це підтверджує, що пін маніфесту в workflow правильний і файли доїхали без
CRLF — тобто шаблон придатний до роздачі.

Потім **Settings → General**, вгорі галочка **Template repository**. З'явиться
кнопка «Use this template».

#### Кожен новий проєкт

*Use this template → Create a new repository* → назва → Create. Локально:

```bash
git clone https://github.com/<ви>/<новий-проєкт>.git
cd <новий-проєкт>
git config core.hooksPath .githooks
python3 scripts/check-template.py
```

Все. Ні розпакування, ні очищення. Коміту тут теж немає: GitHub уже створив
початковий коміт з усіма файлами, тож `git add . && git commit` відповість
«nothing to commit» — так і має бути.

`git config core.hooksPath` доводиться повторювати в кожному проєкті: git
принципово не переносить налаштування хуків ні через клон, ні через шаблон.
Обійти це не можна, тому `check-template.py` і вважає ненастроєний `hooksPath`
помилкою, а не попередженням.

#### Ручний варіант A — порожня папка на диску

```bash
git init
git config core.hooksPath .githooks
python3 scripts/check-template.py
git add . && git commit -m "chore: TASK-000 project template"
```

#### Ручний варіант B — репозиторій створений на GitHub і клонований

Створюйте його **порожнім**: інакше в ньому опиниться чужий `.gitignore`, а
`check-template.py` окремо вимагає в цьому файлі саме `tmpBin/*` і
`!tmpBin/.gitkeep`.

```bash
git clone https://github.com/<ви>/<проєкт>.git
cd <проєкт>
git rm -r --quiet .                        # якщо репозиторій усе-таки не порожній
# розпакувати сюди ВМІСТ папки project-template, поруч із .git
git config core.hooksPath .githooks
python3 scripts/check-template.py
git add . && git commit -m "chore: TASK-000 project template"
git push
```

`git rm -r .` прибирає файли, але не чіпає `.git` — видалення самої `.git`
розірвало б зв'язок із GitHub. Розпаковувати треба саме вміст
`project-template/`, а не папку цілком: зайвий рівень вкладеності — і жодна
перевірка не знайде своїх файлів.

#### Спільне для всіх сценаріїв

Перевірка тут — саме перевірка, а не `--fix`. Правильні хеші вже лежать у
`scripts/integrity.sha256`, і перший прогін підтверджує, що файли доїхали
до вас незміненими. `--fix` першою дією затер би цей baseline і мовчки
узаконив би будь-яку сторонню правку або зіпсований CRLF-checkout.

**Крок 0 робіть у терміналі самі, до того як відкриєте Claude Code чи Codex.**
Не тому, що агент не впорається — команди йому дозволені, — а через порядок.
`stop-integrity.py` ганяє `check-template.py` після кожного ходу агента і при
провалі виходить з кодом 2, тобто блокує завершення ходу. Поки `core.hooksPath`
не заданий, перевірка падає, і перший же хід агента впреться в цей блок.
Зациклення не буде — запобіжник `stop_hook_active` це закриває, — але виглядає
як поломка. У самому кроці 0 жодного рішення немає, делегувати його нічого не
дає.

`TASK-000` — єдиний виняток із правила «кожен `TASK-*` спершу в `BACKLOG.md`»:
на цьому кроці бэклога ще не існує. У сценарії з template repository цей коміт
уже зроблено разово, при викладенні шаблону.

### Крок 1 — вимоги

Нова сесія в чаті. Вставити `prompts/01-ba-interview.md` як інструкцію.
Пройти інтерв'ю → команда «Завершуємо інтерв'ю» → зберегти результат
у `docs/FRS.md`.

Корисно: команда «аудит» перед фіналом — модель критикує власний документ.

### Крок 2 — архітектура

Нова сесія. Вставити `prompts/02-solution-setup.md` і **три входи**: `docs/FRS.md`,
`docs/ADR/ADR-000-template.md` (без нього ADR вийдуть у вигаданому форматі) і
розділ *Environments* із `RulesForAIVibeCoding.md`.
Результат → `docs/ARCHITECTURE.md` + `docs/ADR/ADR-XXX-*.md`.

Наприкінці сесія видасть розділ **«Зміни до FRS»**. Внесіть їх у `docs/FRS.md`,
підніміть версію, допишіть рядок у Change Log — і тільки потім ідіть на крок 3.
Архітектура майже завжди щось міняє у вимогах, а крок 3 читає саме файл: із
розбіжними документами він заблокує половину плану як залежну від `[OPEN]`.

Сесія в чаті не має доступу до репозиторію, тож усе, що вона просить
«додати в `OPEN-QUESTIONS.md`», доведеться перенести туди руками. Не
пропускайте: наступний крок читає саме файл, а не історію чату.

Два розділи довести до кінця обов'язково:

* **Environments & Delivery** — без нього цикл розробки не працює. Тут же
  описується схема скриптів `deploy/` (`install` / `update` / `rollback`):
  мова, цільове середовище, звідки беруться секрети;
* **Project Structure** — там фіксується команда локальної перевірки, на яку
  посилаються цикл розробки і Definition of Done. Якщо в проєкті є UI, вона
  включає й UI-тести (браузерні / візуальні) — окремої команди для них немає.
  Поки її рядок порожній, `check-template.py` видає WARN.

### Крок 3 — план

Нова сесія. Вставити `prompts/03-build-plan.md`, дати FRS + ARCHITECTURE + усі
`docs/ADR/*`. Результат → `docs/BACKLOG.md` із вертикальними зрізами.

Готові документи комітяться як `docs: TASK-000 FRS, architecture and backlog` —
у них немає власного `FR-*`, а хук вимагає ID у першому рядку.

Перший рядок плану — не зріз, а `TASK-001`: тестовий раннер, лінтер, типи
і перевірка, що команда з рядка «Локальна перевірка» справді виконується
(сам рядок заповнює крок 2). Без нього перший же зріз упреться
в глухий кут — цикл вимагає тест і зелену локальну перевірку, а ні того,
ні іншого ще немає. Якщо в проєкті є UI, `TASK-001` ставить і раннер UI-тестів.

Перед першим деплоєм на test у плані стоїть `TASK-*` на скрипти `deploy/`.
Кожен із них, зокрема `rollback`, прогнано локально, а пакет, який вони
доставляють, не містить тестів — це перевіряє сам скрипт.

### Крок 4 — розробка

Відкрити проєкт у Claude Code або Codex. Агент читає `CLAUDE.md` / `AGENTS.md`,
через них — `RulesForAIVibeCoding.md`, далі документацію.

Одна сесія = один зріз із `BACKLOG.md`. Цикл описано в правилах, розділ
*Work cycle*.

Дві команди на кожну сесію, в обох агентах однаково:

| Команда | Що робить |
|---|---|
| `/slice-start` | бере наступний `TODO`, знаходить FR і AC **пошуком за ID**, показує варіанти, зупиняється до коду |
| `/slice-finish` | локальна перевірка, механічний DoD, diff, оновлення BACKLOG, коміт |

У Claude Code це `.claude/commands/`, у Codex — репозиторні скіли в
`.agents/skills/`, які Codex підхоплює сам. Раніше для Codex доводилося
писати «виконай `prompts/dev/slice-start.md`» руками; більше ні.

Робота йде на `main`, гілка — тільки для незавершеного зрізу (`wip/fr-0XX-*`).
Це зафіксовано в правилах, розділ *Work cycle*, підрозділ *Branching*.

Зріз, що додає або змінює UI, отримує UI-тести проти AC — у браузері, плюс
візуальні там, де AC про вигляд. Нові еталонні скріншоти агент сам не приймає:
показує старе й нове зображення і чекає на ваше «так». Правила, розділ
*Work cycle*, підрозділ *UI tests*.

Конфігураційний файл або панель налаштувань, які змінюватиме адміністратор чи
користувач, мають пояснення біля кожного параметра: що він робить, допустимі
значення, значення за замовчуванням, коли зміна набирає сили. Текст пояснень
береться з документів. Якщо в документах його немає, агент ставить питання.
Правила, розділ *Work cycle*, підрозділ *Settings that someone else will
change*.

### Крок 5 — реліз і деплой

Деплой — тільки за вашою явною командою, і він не є кроком циклу. Два
документи, які не дублюють один одного:

* `docs/ARCHITECTURE.md`, розділ *Environments & Delivery* — **схема**:
  середовища, як влаштовано деплой і відкат;
* `docs/DEPLOY.md` — **runbook конкретного релізу**: версія, що змінюється,
  міграції, точні команди `deploy/`, результат локальної перевірки, перевірка
  після деплою, відкат. Створюється на першому релізі, оновлюється на кожному.

Кожен реліз — окремий `TASK-*`. Порядок: агент оновлює `DEPLOY.md` і показує
diff → ваше «так» → коміт → повна локальна перевірка (UI-тести включно) на
збірці релізу → тільки тоді деплой. Червона перевірка — деплою немає. На test і
prod іде один і той самий пакет, без тестів, тестових інструментів і еталонних
скріншотів.

Подробиці — у правилах, розділ *Environments*, підрозділ *Releases and
deployment*.

## Що перевіряється автоматично

Три скрипти, усі без залежностей, лише Python 3.

### `check-template.py` — цілісність

Запускається на кожному коміті (`.githooks/pre-commit`) і в кінці кожного
ходу агента (`hooks.Stop`):

* enforcement-файли не змінювалися (sha256 у `scripts/integrity.sha256`);
* сам маніфест на місці й не вкорочений — його видалення чи обрізання
  більше не «лікує» перевірку;
* структура папок, документів, промтів, команд і хуків на місці —
  список `REQUIRED` дзеркалить розділ *Project structure* правил;
* `.gitignore` містить саме `tmpBin/*` і `!tmpBin/.gitkeep`;
* `core.hooksPath` справді вказує на `.githooks`.

Плюс WARN, які не блокують коміт: документи ще порожні, команда локальної
перевірки не заповнена.

WARN «still the empty template» має зникнути після кроку 3 — промти просять
прибрати з документа шапку «Порожній шаблон…», і саме за нею скрипт відрізняє
заповнений документ від незайманого. Якщо він лишився після того, як ви
заповнили FRS, — шапку не прибрали, і три хибні WARN на кожному коміті
поховають справжні.

**Маніфест пінить не тільки правила.** Він покриває й механізм, який їх
виконує: три скрипти, обидва git-хуки, обидва хуки агента, `settings.json`.
Пінити самі правила було б недостатньо: перевірка, переписана на
`print("OK")`, проходить і pre-commit, і CI, бо CI виконує той самий скрипт.
Хеш самого маніфесту зашитий у `.github/workflows/template-check.yml`:
маніфест не може пінити сам себе, вийшло б коло. Цей пін `--fix` оновлює
сам, тим же запуском — копіювати хеш руками не треба. Ловить він не того,
хто свідомо запустив `--fix` (такий перепише і пін), а маніфест, змінений
**в обхід** `--fix`: підігнаний руками під переписаний скрипт. Такий випадок
`sha256sum -c` пропускає, а розбіжність із піном — ні. Тепер це перевіряється
двічі: `check-template.py` на кожному коміті і CI на сервері.

### `check-ids.py` — traceability за ID

Теж на кожному коміті. Порівнює множини ідентифікаторів і нічого не знає
про формат документів — перейменування розділу його не ламає:

* `SLICE`, який посилається на `FR-*`, якого немає у FRS → **помилка**;
* `AC-*` у тесті або в BACKLOG, якого немає у FRS → **помилка**;
* `FR-*` із FRS, який не згадує жоден зріз → WARN;
* `ADR-*` без файла в `docs/ADR/` → WARN.

Це рівно той клас помилок, який тут найдорожчий: вигаданий ID народжується
на кроках 1–3, у чаті, де перевіряти нема чим, і живе в проєкті місяцями.
Перевірка мовчить, поки FRS порожній.

### `check-slice.py` — механічний Definition of Done

Запускає агент на фініші зрізу: `python3 scripts/check-slice.py SLICE-014`.
Перевіряє статус зрізу, дадений рядок у Progress Log, існування всіх
заявлених вимог у FRS, наявність кожної з них у `source/` (правила вимагають
ID у назві тесту) і нові `TODO`/`FIXME` без запису в `OPEN-QUESTIONS.md`.

`AC-*` зараховується за вимогу, коли обидва ID стоять **в одному рядку** FRS:
заголовок `### AC-001 (FR-001)` і рядок матриці трасування
`| FR-001 | … | AC-001 |` дають правильну пару, і жоден із них не створює
хибної. До 2026-09-16 тут було вікно у 400 символів, і воно не працювало: у
FRS із матрицею трасування — а її вимагає `prompts/01-ba-interview.md` — усі
ID стоять за десятки символів один від одного, тож майже будь-який AC
зараховувався за майже будь-яку вимогу. Рядок DoD про traceability тоді
означав «якийсь тест згадує якийсь AC». `AC-*`, якого жоден рядок не
прив'язує до вимоги, дає WARN — перевірка не тихшає, вона каже, чому.

Чого `check-slice.py` не бачить: що тест саме браузерний. UI-тест у
`*.spec.ts` під `source/` зараховується так само, як будь-який інший, тож
наявність UI-тестів для UI-зрізу — ваша перевірка в diff, а не механічна.

Сенс простий: DoD, який агент переказує, — це DoD, який завжди пройдено.
Те, що можна звести до коду виходу, зведено. Решта — три рядки, які агент
зобов'язаний назвати чесно, і які судите ви. Список короткий навмисно:
кожен неспростовний пункт у чеклісті здешевлює брехню і в спростовних.

### Хук `commit-msg`

Не пропускає коміт без типу
(`feat|fix|refactor|test|docs|chore|build|ci|revert`) і без ID вимоги чи
задачі: `FR|DR|NFR|IR|TASK|SLICE` + рівно три цифри.

`BR-*` у цьому переліку немає навмисно: бізнес-вимога — рівень над `FR`, і
реалізує її та `FR`, що з неї виведена. Коміт на `BR` обірвав би ланцюг
`FR → коміт` саме там, де він потрібен. Щоб відмова не виглядала як хиба
перевірки, хук розпізнає `BR-*` у повідомленні й окремо каже, що робити:
взяти `FR`, яка реалізує цю бізнес-вимогу, а якщо такої немає — написати її. `FR-014` проходить,
`FR-14`, `FR-0141`, `XFR-014` і `FR-014-2` — ні. ID шукається **тільки
в першому рядку**. Обійти свідомо: `git commit --no-verify`.

Якщо `python3` у PATH немає (типово для git-bash на Windows), pre-commit
пробує `python`, а якщо немає й того — падає.

### CI

`.github/workflows/template-check.yml` виконує ті самі скрипти на сервері
плюс звіряє пін маніфесту і теми комітів push-у / PR-у тими самими двома
`grep -E`, що й `commit-msg` (merge-коміти пропускаються, `Revert` звільнено
від типу, але не від ID). Це єдина перевірка, яку не знімає `--no-verify`;
вона ж ловить CRLF, що просочився в репозиторій. Немає GitHub — файл можна
видалити.

## Дозволи агента

`.claude/settings.json` дублює межі з розділу *Environments* правил на рівні
інструментів Claude Code. Це **другий рубіж**: головним лишається текст
правил.

Одне deny-правило звідти прибрано навмисно: `Bash(rm -rf:*)` перехоплювало
команду **до** хука, тож дозвіл прибирати за собою в `tmpBin/` існував лише
на папері. Хук тепер покриває `rm` ширше за те правило — і з винятком, — тож
видалення нічого не послабило.

Але патерни дозволів збігаються з **текстом команди**, тож обходяться
перестановкою прапорця, коротким написанням (`-n` замість `--no-verify`)
чи зайвим `./`. А deny-правила `Read(...)` дістають до Bash лише частково:
Claude Code розбирає прості команди (`cat`, `ls`) і застосовує `Read`-deny до
їхніх шляхів, але не бачить шлях усередині інтерпретатора — `python -c`,
`node -e`, heredoc (перевірено зондом 2026-09-17). Тому те, що патерном не
закривається, винесено в хуки:

* **`.claude/hooks/bash-guard.py`** (PreToolUse на Bash) дивиться на команду,
  яка реально збирається виконатися, і блокує звернення до `.env`, `*.pem`,
  `*.key` і `secrets/` будь-яким інструментом (зокрема через glob і brace
  expansion), `--no-verify` (зокрема склеєний `-nm`, скорочений `--no-veri`
  і після глобальних опцій git: `git -C . commit -n`), force-push прапорцем
  або refspec-ом `+main`, `core.hooksPath` через `-c`, `--config-env` чи
  `GIT_CONFIG_KEY_n` у будь-якому регістрі, підміну `core.hooksPath`, `--fix`
  і сам прапорець `--i-know-what-im-doing`, запис через Bash у
  `scripts/integrity.sha256` і в кожен запінений нею файл (`sed -i`, `cp`,
  `>` — Edit/Write на них питають, а Bash не питав), видалення поза `tmpBin/`
  (зокрема `find -delete`, `-exec rm`, `xargs rm`, `\rm`, `/bin/rm`,
  `command rm`; шлях зі `$` чи `$(…)` — завжди поза `tmpBin/`), `reset
  --hard`, `clean`, `checkout --`, `restore`.

  Плюс `git rm` без `--cached` і `git checkout` без `-b`: обидва прибирають
  або затирають файли, а відрізнити гілку від шляху за текстом неможливо, тож
  гілки міняються через `git switch`.

  Команду хук читає **трьома способами**, бо одного не вистачає: як написано;
  без лапок (`--f""ix` це `--fix`); і без тексту в лапках, але зі збереженими
  прапорцями — щоб повідомлення коміту зі словом `-name` не зійшло за
  `--no-verify`, а `git commit "--no-verify"` таки зійшов.

  Правила, що описують **одну команду** — `rm`, `git rm`, `git checkout`,
  запис у маніфест — застосовуються **посегментно**, а не до всього рядка.
  Живий тест 2026-09-16 показав чому: майже кожна команда агента починається
  з `cd "$PROJECT" &&`, і правило, заякорене на початок рядка, перетворювало
  `cd … && sha256sum -c scripts/integrity.sha256` на «запис у маніфест» —
  на першій же команді сесії. З тієї ж причини `git rm --cached x && git
  status --short` більше не блокується через `r` у `--short`.

  Читання лишається дозволеним там, де воно потрібне: `git config --get
  core.hooksPath`, `cat`/`diff`/`sha256sum -c` на маніфесті,
  `--force-with-lease`, `rm` усередині `tmpBin/` — зокрема після `cd` туди й
  у зв'язці з іншими командами. `os.environ` і `config.environment` більше не
  приймаються за файл `.env`.

  Хук читає з payload ще й **робочу директорію**. Без неї голий
  `rm scratch.txt`, набраний усередині `tmpBin/`, не відрізнити від такого ж
  у корені проєкту — і другий живий тест показав, що це було єдине справжнє
  хибне спрацювання, яке лишалося. `rm`, `unlink`, `truncate` і
  `find -delete` живуть під одним правилом і одним винятком: різниця між
  ними лише в написанні.

  Додано й `git stash drop` / `git stash clear`: агент, якому заблокували
  `git restore`, тягнеться саме до них — ефект той самий, а відкоту немає.

  Межа названа чесно в докстрінгу хука: Bash — інтерпретатор, і жоден патерн
  не закриває `$(printf …)` чи base64. Хук піднімає ціну випадкового обходу,
  а не навмисного. Те, що не залежить від читання тексту, — це `pre-commit`
  і пін маніфесту в CI.
* **`.claude/hooks/stop-integrity.py`** (Stop) проганяє перевірку цілісності.
  Важлива деталь: зупинку блокує і показує повідомлення агенту **тільки код
  виходу 2**; при 1 агент про проблему не дізнається. Хук виходить з 2 і має
  обов'язковий запобіжник на `stop_hook_active` — без нього Stop-хук
  крутить агента до таймауту. Спрацьовує він після кожного ходу, а не раз
  за сесію: так влаштована подія Stop.

`--fix` захищений не патерном, а самим скриптом: потрібен другий прапорець
`--i-know-what-im-doing` **і** термінал. Перейменуванням команди термінал не
отримати, але `script -qec "…" /dev/null` видає псевдотермінал, і `isatty()`
каже «так» — перевірено. Для Claude Code це закриває `bash-guard.py`: у тексті
такої команди `--fix` лишається видимим, і вона блокується (теж перевірено).
Для агента без цього хука — наприклад Codex — межу тримає approval policy в
`~/.codex/config.toml`, а не прапорець.

`ask` стоїть на редагуванні всього, що є домовленістю або механізмом:
FRS, ARCHITECTURE, `docs/ADR/**`, `scripts/**`, `.githooks/**`,
`.claude/**`, `.github/**` — і на `Edit`, і на `Write`, бо це різні
інструменти. `BACKLOG.md` навмисно не в списку: агент штатно править у ньому
статус і Progress Log, а межі того, що йому там можна, тримає текст правил.

Локальні відхилення — у `.claude/settings.local.json` (він у `.gitignore`).
Там же змінюйте `python3` на `python`, якщо у вас Windows без аліаса.

Для Codex аналог налаштовується не тут, а в `~/.codex/config.toml`
(approval policy + sandbox). Шаблон його не несе — це машинна, а не проєктна
конфігурація.

## Ключова домовленість

**Наскрізний ключ — `FR-ID`.** Він доживає від вимоги до тесту й коміту:

```
BR-001 → FR-001 → ADR-003 → SLICE-014 → AC-021 → commit
```

Робота, що не мапиться на жоден `FR-*` (CI, лінтери, залежності, борг), —
це `TASK-*` у розділі Tech Tasks. Дефекти лишаються на `FR-*` тієї вимоги,
яку вони порушують. Решта домовленостей — у правилах.

## Якщо документація застаріла

Вимоги змінилися посеред розробки — повернутися в сесію відповідного кроку,
оновити документ, підняти версію, дописати рядок у Change Log, і тільки потім
продовжувати кодити. Не правити код в обхід FRS: тоді traceability ламається
і план перестає відповідати реальності.

## Якщо перевірка цілісності падає без причини

Спершу подивіться на закінчення рядків. При `core.autocrlf=true` на Windows
робоча копія отримує CRLF, і хеші не збігаються ніколи. `.gitattributes`
це закриває для нових клонів; для наявного — `git add --renormalize .`.
`--fix` у такій ситуації не лікує, а затирає baseline.

Єдиний законний привід для `--fix` — enforcement-файл змінено за вашим
погодженням. `--fix` перепише і `integrity.sha256`, і пін у workflow; обидва
файли йдуть **тим самим комітом**, що й сама зміна.

## Windows

Термінал — **Git Bash**, не PowerShell і не cmd: хуки починаються з
`#!/bin/sh`. У Провіднику: правий клік на порожньому місці в папці проєкту →
*Open Git Bash here* (у Windows 11 спершу «Показати додаткові параметри»).

### Заглушка `python3`

Перше, що треба зробити на новій машині:

```bash
python3 --version
```

Windows 10/11 кладе в PATH заглушку `python3.exe`, яка відкриває Microsoft
Store. Ознака — вивід `Python` без номера версії, або порожньо, або відкрився
магазин. Перевірити напевно: `which python3` покаже шлях усередині
`AppData/Local/Microsoft/WindowsApps`.

Це гірше за просту відсутність Python. `pre-commit` уміє перемикатися з
`python3` на `python`, але вибирає за `command -v python3` — а заглушка на цю
перевірку відповідає «є». Тобто запасний варіант не спрацьовує, і хук запускає
порожнечу.

Найчистіше рішення — зробити `python3` справжнім, а не обходити його. Якщо
`python --version` віддає нормальну версію, Python установлений і заважає лише
заглушка:

```bash
cp /c/Users/<ви>/AppData/Local/Programs/Python/Python3XX/python.exe \
   /c/Users/<ви>/AppData/Local/Programs/Python/Python3XX/python3.exe
```

Перезапустити Git Bash, перевірити `python3 --version`. Копія `python.exe` під
іншим ім'ям — повноцінний інтерпретатор: він знаходить свою установку за
розташуванням файлу.

Після цього `python3` працює скрізь — у git-хуках, у `.claude/settings.json`,
у всіх командах із цього README, — і жодних машинних відхилень від шаблону не
потрібно.

Якщо після перезапуску `python3` усе ще заглушка, значить `WindowsApps` у PATH
стоїть раніше: *Параметри → Програми → Додаткові параметри програм → Псевдоніми
виконання програм* — зняти перемикач для `python3.exe`.

Python узагалі не встановлений (`python` і `py` теж без версії) — беріть із
python.org, при встановленні галочка **Add python.exe to PATH**.

### Якщо `python3` зробити не вдалося

Запасний шлях, якщо у вас є тільки `python`. Git-хуки виживуть самі —
`pre-commit` перемкнеться, побачивши відсутність `python3`. А от хуки агента ні:
`.claude/settings.json` викликає `python3` жорстко, і правити цей файл не можна,
він у маніфесті. Відхилення йде в `.claude/settings.local.json` — він у
`.gitignore` і в репозиторій не потрапляє:

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command",
          "command": "python \"$CLAUDE_PROJECT_DIR/.claude/hooks/bash-guard.py\"" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
          "command": "python \"$CLAUDE_PROJECT_DIR/.claude/hooks/stop-integrity.py\"" }] }
    ]
  }
}
```

### `--fix` у Git Bash не запускається

`python3 scripts/check-template.py --fix --i-know-what-im-doing` у Git Bash
відповідає `ERROR: --fix only runs from a terminal` — хоча термінал у вас перед
очима. Це не хиба перевірки: MinTTY, термінал Git Bash, віддає програмам
**пайп**, а не консоль Windows, тож `isatty()` бачить те саме, що побачив би у
скрипті чи в агента.

Запускайте `--fix` із **PowerShell або cmd** — там консоль справжня:

```powershell
cd D:\code\<проєкт>
python scripts\check-template.py --fix --i-know-what-im-doing
```

Решта команд із цього README працює в Git Bash як завжди: обмеження стосується
тільки `--fix`, бо тільки він вимагає терміналу. Хто не хоче перемикати вікно —
`winpty python scripts/check-template.py --fix --i-know-what-im-doing`.

### Кодування виводу

Скрипти друкують українською, а Git Bash на Windows бере кодування консолі —
і `WARN` про `Локальна перевірка` виходить кракозябрами, тобто саме та мітка,
яку треба прочитати, стає нечитабельною. Один рядок у `~/.bashrc`:

```bash
export PYTHONUTF8=1
```

### Закінчення рядків

Окремо налаштовувати нічого не треба: `.gitattributes` жорстко ставить
`eol=lf` для всього текстового, включно з `.githooks/*` і
`scripts/integrity.sha256`, і потрапляє в перший же коміт. Ознака, що щось
пішло не так — `check-template.py` скаржиться на хеші файлів, яких ви не
чіпали. Лікується `git add --renormalize .`, а не `--fix`.
