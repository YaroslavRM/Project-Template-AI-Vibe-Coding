# scripts/

| Файл | Призначення |
|---|---|
| `check-template.py` | enforcement-файли не змінені + структура на місці + хуки увімкнені |
| `check-ids.py` | traceability за ID: ніщо не посилається на вимогу, якої немає у FRS |
| `check-slice.py` | механічна частина Definition of Done для одного зрізу |
| `integrity.sha256` | пінені хеші всіх enforcement-файлів |

```bash
python3 scripts/check-template.py                              # перевірити
python3 scripts/check-ids.py                                   # traceability
python3 scripts/check-slice.py SLICE-014                       # DoD зрізу
python3 scripts/check-template.py --fix --i-know-what-im-doing # оновити baseline
```

`check-template.py` і `check-ids.py` запускаються автоматично з
`.githooks/pre-commit`. Усі три потребують лише Python 3, без залежностей.

## Що саме читається в `source/`

`check-ids.py` і `check-slice.py` беруть список файлів не обходом папки, а в
git:

```bash
git ls-files -z --cached --others --exclude-standard -- source
```

Тобто відстежувані файли плюс невідстежувані, яких не виключає `.gitignore`.
Це і є «власний код проєкту», і воно не потребує супроводу під кожен стек:
`source/vendor` у PHP-проєкті, `target/` у Rust чи кеш модулів у Go випадають
самі, бо проєкт їх уже ігнорує.

Причина не тільки в швидкості. Чужий код — не код проєкту: `AC-123`, що
випадково трапився у вендореній залежності чи в її changelog, `check-ids.py`
раніше вважав вигаданим ID і блокував коміт.

Два запобіжники лишаються:

* `SKIP_DIRS` — резерв на випадок, коли git недоступний або це не репозиторій;
  тоді скрипт друкує WARN і обходить папку за списком імен;
* `TEXT_SUFFIXES` + `MAX_BYTES` — діють завжди, навіть на git-список:
  закомічена фікстура на 200 МБ теж не місце для пошуку ID у назві тесту.

Напрямок відмови безпечний: порожній список означає «жодна вимога не
знайдена в `source/`», тобто перевірка падає, а не мовчки проходить.

Наслідок, про який варто знати: заігнорований файл більше не зараховується як
тест. Це суворіше, ніж було, і навмисно — тесту, якого немає в репозиторії,
для traceability не існує.

## Маніфест

`integrity.sha256` пінить не тільки правила, а й механізм, який їх виконує:
три скрипти, обидва git-хуки, обидва хуки агента і `settings.json`.
Пінити самі правила недостатньо — перевірка, переписана на `print("OK")`,
проходить і pre-commit, і CI.

Сам маніфест покрити маніфестом не можна — вийде коло. Його хеш зашитий
окремо в `.github/workflows/template-check.yml`, який з тієї ж причини
у маніфест не входить: ланцюг workflow → маніфест → решта, без циклу.

Пін оновлює `--fix`, тим же запуском. Раніше його копіювали руками, і це
нічого не давало: хто зміг запустити `--fix`, той і рядок у workflow
перепише. Єдине, що давав ручний крок, — коміти із забутим піном.

Що пін ловить насправді — маніфест, змінений **в обхід** `--fix`: підігнаний
руками під переписаний скрипт. `sha256sum -c` на такому проходить, пін — ні.
Перевіряється в двох місцях: `check-template.py` (блокує коміт) і CI
(`--no-verify` його не дістає). Проєкт без GitHub може видалити workflow —
тоді пінити нема де, і обидві перевірки мовчать.

## `--fix`

Свідома дія, і навмисно незручна: потрібен другий прапорець
`--i-know-what-im-doing` **і** термінал. Причина конкретна — заборона в
`settings.json` збігається з текстом команди, тож обходиться перестановкою
(`python3 ./scripts/check-template.py --fix`). Термінал так не підробиш.

Але й терміналу самого по собі не досить: `script -qec "…" /dev/null` видає
процесу псевдотермінал, і `isatty()` каже «так». **Перевірено запуском.**

Для Claude Code це закриває `bash-guard.py` — він дивиться на текст команди, а
`--fix` там лишається видимим; окремо блокується й сам `--i-know-what-im-doing`,
тож копія скрипта під іншим ім'ям теж не проходить. Обидва випадки перевірені.
Для агента без такого хука (наприклад, Codex) tty — не бар'єр, і межу тримає
approval policy в `~/.codex/config.toml`, а не цей прапорець.

Оновлює `--fix` два файли: `integrity.sha256` і пін у workflow. Обидва
комітяться разом зі зміною, яку ви погодили.

Якщо `integrity.sha256` зник, скрипт не перебудовує baseline мовчки, а падає:
інакше зміну правил можна було б «узаконити» видаленням одного файлу.

Хеш не збігається, а нічого ви не чіпали — перевірте CRLF (див.
`.gitattributes`), перш ніж тягнутися до `--fix`.
